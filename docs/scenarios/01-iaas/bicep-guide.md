# Scenario 01: Bicep guide

Step by step guide for reproducing Scenario 01 with Bicep.

The original environment was created manually in the Azure portal and is documented in [portal-guide.md](portal-guide.md). This guide rebuilds the same infrastructure as code, so each portal step maps to a piece of Bicep.

> Before adding outputs or screenshots, hide subscription ID, tenant ID, email addresses and public IPs.

**Date built:** 2026 October

---

## Approach

The Bicep version is deployed side by side with the portal version, in its own resource group, so both can exist at the same time. Every name gets a `-bicep` suffix.

| Portal step | Bicep file | Notes |
|---|---|---|
| 1. Resource group | `main.bicep` | Subscription scope |
| 2. Budget alert | `modules/budget.bicep` | |
| 3. Virtual network | `modules/network.bicep` | |
| 4. Network security group | `modules/network.bicep` | SSH rule not created (Bastion is used) |
| 5. Storage account | `modules/storage.bicep` | Public access from all networks (portal used selected networks) |
| 6. Virtual machine | `modules/compute.bicep` | Public IP, NIC, VM, disks, auto shutdown |
| 7. Role assignment | `modules/roles.bicep` | |
| 8. DNS | `modules/dns.bicep` | Record only. The zone already exists in `rg-wehobby-shared` |
| 9a. Bastion Developer | `modules/bastion.bicep` | |
| 9b, 9c. Data disk, Docker | `cloud-init.yaml` | Runs on the first boot |
| 9d onwards. Compose stack, app | Not in Bicep | Application deployment stays separate |

Folder structure:

```text
docs/scenarios/01-iaas/bicep/
├── main.bicep            # subscription scope: resource group + modules
├── main.bicepparam       # parameter values
├── cloud-init.yaml       # first boot VM configuration
└── modules/
    ├── network.bicep     # NSG, VNet, subnet
    ├── storage.bicep     # storage account, photos container
    ├── compute.bicep     # public IP, NIC, VM, data disk, auto shutdown
    ├── roles.bicep       # Storage Blob Data Contributor for the VM identity
    ├── bastion.bicep     # Bastion Developer
    ├── dns.bicep         # alias record in the shared DNS zone
    └── budget.bicep      # budget with 3 alerts
```

All commands run from the root of the `wehobby` repository, in PowerShell.

## Step 2: Create main.bicep

Create `docs/scenarios/01-iaas/bicep/main.bicep` with the scope, the first parameters and the tags:

```bicep
targetScope = 'subscription'

param location string = 'northeurope'
param resourceGroupName string = 'rg-wehobby-iaas-dev-bicep'

var tags = {
  project: 'wehobby'
  environment: 'dev'
  managed_by: 'bicep'
  scenario: '01-iaas'
}
```

| Line | Why |
|---|---|
| `targetScope = 'subscription'` | A resource group is created at subscription level, so the main file runs there |
| `param` | Values that can change between deployments |
| `var tags` | The same four tags as the portal, with `managed_by: bicep` |

## Step 3: Add the resource group

The syntax for any resource is:

```text
resource <symbolic name> '<resource type>@<API version>' = { ... }
```

Add to `main.bicep`:

```bicep
resource resourceGroup 'Microsoft.Resources/resourceGroups@2024-03-01' = {
  name: resourceGroupName
  location: location
  tags: tags
}
```

Validate:

```powershell
az bicep build --file docs/scenarios/01-iaas/bicep/main.bicep
```

No output means it compiled. A `main.json` file (the ARM template) is created next to it.

> **Good to know:** `main.json` is a build artifact. Add `*.json` under the bicep folder to `.gitignore`, or delete it after each build.

```powershell
az deployment sub what-if --name wehobby-bicep-preview --location northeurope --template-file docs/scenarios/01-iaas/bicep/main.bicep
```

Output:

```text
Resource and property changes are indicated with this symbol:
  = Nochange

  = resourceGroups/rg-wehobby-iaas-dev-bicep [2024-03-01]

Resource changes: 1 no change.
```

Before the first deployment Azure showed `+ Create`. Now the desired state already matches Azure, so nothing changes. This is **idempotency**: deploying the same template again does not create duplicates.

```text
Bicep desired state
        |
        v
Azure actual state
        |
        v
Compare
        |
        +---- Difference exists ----> Change resource
        |
        +---- Already matches ------> No change
```

## Step 7: Network module (portal steps 3 and 4)

Create `docs/scenarios/01-iaas/bicep/modules/network.bicep`:

```bicep
param location string
param tags object

var virtualNetworkName = 'vnet-wehobby-iaas-dev-bicep'
var subnetName = 'snet-app'

resource networkSecurityGroup 'Microsoft.Network/networkSecurityGroups@2025-01-01' = {
  name: 'nsg-wehobby-iaas-dev-bicep'
  location: location
  tags: tags
  properties: {
    // Rules are declared inline. A separate securityRules resource gets
    // removed and re-added every time the NSG itself is redeployed.
    securityRules: [
      {
        name: 'Allow-HTTP-HTTPS'
        properties: {
          description: 'Allow inbound HTTP and HTTPS traffic'
          protocol: 'Tcp'
          sourcePortRange: '*'
          destinationPortRanges: [
            '80'
            '443'
          ]
          sourceAddressPrefix: 'Internet'
          destinationAddressPrefix: '*'
          access: 'Allow'
          priority: 100
          direction: 'Inbound'
        }
      }
    ]
  }
}

resource virtualNetwork 'Microsoft.Network/virtualNetworks@2025-01-01' = {
  name: virtualNetworkName
  location: location
  tags: tags
  properties: {
    addressSpace: {
      addressPrefixes: [
        '10.10.0.0/16'
      ]
    }
    // Subnets are declared inline. If the VNet is redeployed without them,
    // Azure tries to delete the subnet, which fails once a NIC uses it.
    subnets: [
      {
        name: subnetName
        properties: {
          addressPrefix: '10.10.1.0/24'
          defaultOutboundAccess: false
          networkSecurityGroup: {
            id: networkSecurityGroup.id
          }
          serviceEndpoints: [
            {
              service: 'Microsoft.Storage.Global'
              locations: [
                '*'
              ]
            }
          ]
        }
      }
    ]
  }
}

output virtualNetworkName string = virtualNetwork.name
output virtualNetworkId string = virtualNetwork.id
output subnetName string = subnetName
output subnetId string = resourceId('Microsoft.Network/virtualNetworks/subnets', virtualNetworkName, subnetName)
output networkSecurityGroupName string = networkSecurityGroup.name
output networkSecurityGroupId string = networkSecurityGroup.id
```

| Setting | Portal equivalent |
|---|---|
| `addressPrefixes: 10.10.0.0/16` | IP addresses → Address space |
| `subnets[0]` | Edit the default subnet → `snet-app`, `10.10.1.0/24` |
| `serviceEndpoints` | Subnet → Service endpoints → `Microsoft.Storage.Global` |
| `networkSecurityGroup` on the subnet | NSG → Subnets → Associate |
| `defaultOutboundAccess: false` | Private subnet (the portal default for new VNets) |
| No SSH rule | `Allow-SSH-MyIP` was deleted after Bastion was set up (portal step 9a) |

> **Good to know:** the first version of this module declared the subnet and the NSG rule as separate child resources (`virtualNetworks/subnets` and `networkSecurityGroups/securityRules`). It deploys fine once, but on every redeploy the parent is sent without its children, so Azure tries to remove them. Once the VM's NIC is in the subnet, that fails with `InUseSubnetCannotBeDeleted`. Declaring children inline in the parent avoids it. Microsoft recommends this in [Create virtual network resources by using Bicep](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/scenarios-virtual-networks).

> **Good to know:** the subnet ID is built with `resourceId()` instead of reading it from the VNet, because inline subnets don't have their own symbolic name.

## Step 9: Storage module (portal step 5)

Create `docs/scenarios/01-iaas/bicep/modules/storage.bicep`:

```bicep
param location string
param tags object

@minLength(3)
@maxLength(24)
param storageAccountName string

resource storageAccount 'Microsoft.Storage/storageAccounts@2025-01-01' = {
  name: storageAccountName
  location: location
  tags: tags
  sku: {
    name: 'Standard_LRS'
  }
  kind: 'StorageV2'
  properties: {
    accessTier: 'Hot'
    allowBlobPublicAccess: false
    allowSharedKeyAccess: true
    defaultToOAuthAuthentication: false
    isHnsEnabled: false
    minimumTlsVersion: 'TLS1_2'
    publicNetworkAccess: 'Enabled'
    supportsHttpsTrafficOnly: true
    // Public network access: enabled from all networks
    networkAcls: {
      bypass: 'AzureServices'
      defaultAction: 'Allow'
    }
  }
}

resource blobService 'Microsoft.Storage/storageAccounts/blobServices@2025-01-01' = {
  name: 'default'
  parent: storageAccount
}

resource photosContainer 'Microsoft.Storage/storageAccounts/blobServices/containers@2025-01-01' = {
  name: 'photos'
  parent: blobService
  properties: {
    publicAccess: 'None'
  }
}

output storageAccountName string = storageAccount.name
output storageAccountId string = storageAccount.id
output blobEndpoint string = storageAccount.properties.primaryEndpoints.blob
output photosContainerName string = photosContainer.name
```

| Setting | Portal equivalent |
|---|---|
| `Standard_LRS`, `StorageV2` | Performance Standard, Redundancy LRS |
| `allowBlobPublicAccess: false` | Allow enabling anonymous access on containers: off |
| `allowSharedKeyAccess: true` | Enable storage account key access: on |
| `minimumTlsVersion: TLS1_2` | Minimum TLS version 1.2 |
| `isHnsEnabled: false` | Hierarchical namespace off |
| `publicNetworkAccess: Enabled` + `defaultAction: Allow` | Public network access: enabled from all networks |
| `photos` container, `publicAccess: None` | Container `photos`, private access |

> **Good to know:** storage account names are global across all of Azure. `stwehobbyiaasdev` is already taken by the portal version, so the Bicep version is `stwehobbyiaasdevbicep` (21 characters, the limit is 24).

> **Good to know:** "all networks" removes the network layer, not the authentication. The `photos` container is still private (`publicAccess: None`, `allowBlobPublicAccess: false`), so every request still needs a Microsoft Entra token, a SAS token or the account key. Anonymous requests get `404` / `403`.

> **Good to know:** to lock it down later like the portal version, set `defaultAction: 'Deny'` and add `virtualNetworkRules` with the `snet-app` subnet ID (and `ipRules` with your client IP to browse it from the portal). The subnet already has the `Microsoft.Storage.Global` service endpoint, so no network change is needed.

## Step 10: Compute module (portal step 6)

Create `docs/scenarios/01-iaas/bicep/modules/compute.bicep`:

```bicep
param location string
param tags object
param subnetId string

param vmName string = 'vm-wehobby-iaas-dev-bicep-01'
param vmSize string = 'Standard_B2als_v2'
param adminUsername string = 'azureuser'

@description('SSH public key content')
param adminPublicKey string

@description('cloud-init file, base64 encoded. Only used on the first boot.')
param customData string

param dataDiskSizeGB int = 32
param autoShutdownTime string = '1900'
param autoShutdownTimeZone string = 'GMT Standard Time'

// ---------- Public IP ----------

resource publicIp 'Microsoft.Network/publicIPAddresses@2025-01-01' = {
  name: 'pip-${vmName}'
  location: location
  tags: tags
  sku: {
    name: 'Standard'
    tier: 'Regional'
  }
  properties: {
    publicIPAllocationMethod: 'Static'
    publicIPAddressVersion: 'IPv4'
    dnsSettings: {
      domainNameLabel: 'wehobby-iaas-dev-bicep'
    }
  }
}

// ---------- Network interface (no NSG, the subnet NSG controls access) ----------

resource networkInterface 'Microsoft.Network/networkInterfaces@2025-01-01' = {
  name: 'nic-${vmName}'
  location: location
  tags: tags
  properties: {
    ipConfigurations: [
      {
        name: 'ipconfig1'
        properties: {
          privateIPAllocationMethod: 'Dynamic'
          subnet: {
            id: subnetId
          }
          publicIPAddress: {
            id: publicIp.id
          }
        }
      }
    ]
  }
}

// ---------- Virtual machine ----------

resource virtualMachine 'Microsoft.Compute/virtualMachines@2024-11-01' = {
  name: vmName
  location: location
  tags: tags
  identity: {
    type: 'SystemAssigned'
  }
  properties: {
    hardwareProfile: {
      vmSize: vmSize
    }
    osProfile: {
      computerName: vmName
      adminUsername: adminUsername
      customData: customData
      linuxConfiguration: {
        disablePasswordAuthentication: true
        ssh: {
          publicKeys: [
            {
              path: '/home/${adminUsername}/.ssh/authorized_keys'
              keyData: adminPublicKey
            }
          ]
        }
      }
    }
    storageProfile: {
      imageReference: {
        publisher: 'Canonical'
        offer: 'ubuntu-24_04-lts'
        sku: 'server'
        version: 'latest'
      }
      osDisk: {
        name: 'osdisk-${vmName}'
        createOption: 'FromImage'
        managedDisk: {
          storageAccountType: 'StandardSSD_LRS'
        }
      }
      dataDisks: [
        {
          name: 'disk-${vmName}-data'
          lun: 0
          createOption: 'Empty'
          diskSizeGB: dataDiskSizeGB
          managedDisk: {
            storageAccountType: 'StandardSSD_LRS'
          }
        }
      ]
    }
    networkProfile: {
      networkInterfaces: [
        {
          id: networkInterface.id
        }
      ]
    }
    securityProfile: {
      securityType: 'TrustedLaunch'
      uefiSettings: {
        secureBootEnabled: true
        vTpmEnabled: true
      }
    }
    diagnosticsProfile: {
      bootDiagnostics: {
        enabled: true // no storageUri = managed storage account
      }
    }
  }
}

// ---------- Auto shutdown ----------

resource autoShutdown 'Microsoft.DevTestLab/schedules@2018-09-15' = {
  name: 'shutdown-computevm-${vmName}'
  location: location
  tags: tags
  properties: {
    status: 'Enabled'
    taskType: 'ComputeVmShutdownTask'
    dailyRecurrence: {
      time: autoShutdownTime
    }
    timeZoneId: autoShutdownTimeZone
    targetResourceId: virtualMachine.id
    notificationSettings: {
      status: 'Disabled'
    }
  }
}

output vmName string = virtualMachine.name
output principalId string = virtualMachine.identity.principalId
output publicIpId string = publicIp.id
output publicIpAddress string = publicIp.properties.ipAddress
output fqdn string = publicIp.properties.dnsSettings.fqdn
```

| Setting | Portal equivalent |
|---|---|
| `publicIp`, Standard, Static | Networking → Public IP → create new |
| `domainNameLabel` | Public IP → Configuration → DNS name label |
| NIC with no `networkSecurityGroup` | NIC network security group: None |
| `identity: SystemAssigned` | Management → System assigned managed identity: on |
| `imageReference` Canonical `ubuntu-24_04-lts` `server` | Image: Ubuntu Server 24.04 LTS |
| `vmSize: Standard_B2als_v2` | Size: B2als v2 |
| `disablePasswordAuthentication` + `publicKeys` | Authentication: SSH public key |
| `osDisk` `StandardSSD_LRS` | OS disk type: Standard SSD |
| `dataDisks` LUN 0, 32 GiB, `Empty` | Create and attach a new disk |
| `securityType: TrustedLaunch` | Security type: Trusted launch (portal default for this image) |
| `bootDiagnostics.enabled` with no `storageUri` | Boot diagnostics: enable with managed storage account |
| `Microsoft.DevTestLab/schedules` | Management → Auto shutdown |
| `customData` | Advanced → Custom data (cloud-init, step 11) |

> **Good to know:** auto shutdown is not a property of the VM. The portal creates a separate resource of type `Microsoft.DevTestLab/schedules`, and its name must be exactly `shutdown-computevm-<vmName>`.

> **Good to know:** to find the image values for another version, run `az vm image list --publisher Canonical --offer ubuntu-24_04-lts --all --output table`.

> **Good to know:** `GMT Standard Time` is the Windows time zone ID for Lisbon and London, including summer time. List the IDs with `[System.TimeZoneInfo]::GetSystemTimeZones() | Select-Object Id`.

## Step 11: cloud-init (portal steps 9b and 9c)

In the portal the data disk and Docker were configured by hand through Bastion. With Bicep, a cloud-init file passed as `customData` does it automatically on the first boot.

Create `docs/scenarios/01-iaas/bicep/cloud-init.yaml`:

```yaml
#cloud-config
# Runs once, on the first boot of the VM.
# Reproduces portal guide steps 9b (data disk) and 9c (Docker).

# 9b. Partition, format and mount the data disk (LUN 0)
disk_setup:
  /dev/disk/azure/scsi1/lun0:
    table_type: gpt
    layout: true
    overwrite: false

fs_setup:
  - device: /dev/disk/azure/scsi1/lun0
    partition: 1
    filesystem: ext4
    label: datadisk

mounts:
  - ["/dev/disk/azure/scsi1/lun0-part1", "/datadisk", "ext4", "defaults,nofail", "0", "2"]

# 9c. Docker prerequisites and log driver
package_update: true
packages:
  - ca-certificates
  - curl

write_files:
  - path: /etc/docker/daemon.json
    content: |
      {"log-driver":"local"}

runcmd:
  - install -m 0755 -d /etc/apt/keyrings
  - curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
  - chmod a+r /etc/apt/keyrings/docker.asc
  - sh -c 'echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" > /etc/apt/sources.list.d/docker.list'
  - apt-get update
  - apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
  - usermod -aG docker azureuser
  # 9b.5 and 9d.1 folders

```

| Section | Portal guide step | Manual command it replaces |
|---|---|---|
| `disk_setup` | 9b.2 | `parted ... mklabel gpt mkpart ...` |
| `fs_setup` | 9b.2 | `mkfs.ext4 -L datadisk ...` |
| `mounts` | 9b.3, 9b.4 | `mount` and the `/etc/fstab` line with `nofail` |
| `packages` | 9c.1 | `apt-get install ca-certificates curl` |
| `write_files` | 9c.7 | `/etc/docker/daemon.json` with the `local` log driver |
| `runcmd` | 9c.2 to 9c.6, 9b.5, 9d.1 | Docker repository, install, `docker` group, folders |

It is loaded in `main.bicep` with:

```bicep
customData: loadFileAsBase64('cloud-init.yaml')
```

> **Good to know:** the first line must be exactly `#cloud-config`, or cloud-init ignores the file.

> **Good to know:** `customData` is only used when the VM is created. Azure refuses to change it on an existing VM. To test a new cloud-init, delete and recreate the VM.

> **Good to know:** `overwrite: false` means cloud-init only partitions the disk if it has no partition table. If the VM is ever recreated with an existing data disk, the data is not wiped.

> **Good to know:** the `mounts` line uses the LUN path instead of a UUID, because the UUID is only known after formatting. The `/dev/disk/azure/scsi1/lun0-part1` path is stable across reboots, as explained in portal step 9b.

## Step 12: Role assignment module (portal step 7)

Create `docs/scenarios/01-iaas/bicep/modules/roles.bicep`:

```bicep
param storageAccountName string

@description('Principal ID of the VM system assigned managed identity')
param principalId string

// Built-in role: Storage Blob Data Contributor
var storageBlobDataContributorRoleId = 'ba92f5b4-2d11-453d-a403-e96b0029c9fe'

resource storageAccount 'Microsoft.Storage/storageAccounts@2025-01-01' existing = {
  name: storageAccountName
}

resource blobDataContributor 'Microsoft.Authorization/roleAssignments@2022-04-01' = {
  // guid() gives the same name on every deployment, so the assignment is not duplicated
  name: guid(storageAccount.id, principalId, storageBlobDataContributorRoleId)
  scope: storageAccount
  properties: {
    roleDefinitionId: subscriptionResourceId('Microsoft.Authorization/roleDefinitions', storageBlobDataContributorRoleId)
    principalId: principalId
    principalType: 'ServicePrincipal'
  }
}
```

| Setting | Why |
|---|---|
| `existing` | References the storage account created by the storage module, without redeploying it |
| `scope: storageAccount` | The role applies to this account only, like IAM on the account in the portal |
| `guid(...)` | Role assignment names must be GUIDs. The same inputs always produce the same GUID, which keeps the deployment idempotent |
| `principalType: ServicePrincipal` | Managed identities are service principals. Setting it avoids a replication delay error right after the VM is created |

> **Good to know:** the role ID `ba92f5b4-2d11-453d-a403-e96b0029c9fe` is the same in every tenant. Find others with `az role definition list --name "Storage Blob Data Contributor" --query "[].name"`.

> **Good to know:** creating role assignments needs Owner or User Access Administrator on the scope. Contributor is not enough.

## Step 14: DNS module (portal step 8)

The DNS zone `wehobby.app` already exists in `rg-wehobby-shared`, with a delete lock, and Porkbun already points to its nameservers. Bicep does not create the zone again. It only adds a record.

Create `docs/scenarios/01-iaas/bicep/modules/dns.bicep`:

```bicep
// Deployed into the shared resource group (rg-wehobby-shared).
// The zone already exists and is protected by a delete lock, so it is referenced, not created.

param zoneName string
param recordName string
param publicIpId string

resource dnsZone 'Microsoft.Network/dnsZones@2018-05-01' existing = {
  name: zoneName
}

resource aliasRecord 'Microsoft.Network/dnsZones/A@2018-05-01' = {
  parent: dnsZone
  name: recordName
  properties: {
    TTL: 3600
    targetResource: {
      id: publicIpId
    }
  }
}

output fqdn string = '${recordName}.${zoneName}'
```

| Setting | Portal equivalent |
|---|---|
| `existing` zone | The zone created in step 8b |
| `dnsZones/A` | Recordsets → Add → Type A |
| `targetResource` | Alias record set: Yes, Azure resource: the public IP |
| `TTL: 3600` | TTL 1 hour |

The module is called from `main.bicep` with a different scope:

```bicep
scope: az.resourceGroup(sharedResourceGroupName)
```

> **Good to know:** the record is `iaas-bicep`, not `iaas`, `@` or `www`. Those point to the portal VM, which serves the real site. Pointing them at the Bicep VM would take the site offline.

> **Good to know:** the delete lock on `rg-wehobby-shared` allows creating and updating records, so the deployment works with the lock in place. Deleting the record later needs the lock removed (step 19).

> **Good to know:** `az.resourceGroup(...)` has the `az.` prefix because `main.bicep` already has a resource with the symbolic name `resourceGroup`, which hides the built in function.

## Step 20: Tear down

Everything in `rg-wehobby-iaas-dev-bicep` goes with the resource group:

```powershell
az group delete --name rg-wehobby-iaas-dev-bicep --yes --no-wait
```

The DNS record lives in `rg-wehobby-shared`, so it stays. Once the public IP is deleted, the alias record stops resolving (no dangling DNS), but the record set remains. The delete lock also applies to the record sets inside the resource group, so remove it temporarily to clean up:

```powershell
az lock delete --name lock-wehobby-shared --resource-group rg-wehobby-shared
az network dns record-set a delete --resource-group rg-wehobby-shared --zone-name wehobby.app --name iaas-bicep --yes
az lock create --name lock-wehobby-shared --resource-group rg-wehobby-shared --lock-type CanNotDelete
```

> **Good to know:** recreating the environment is just step 18c again. That's the main benefit over the portal version: the whole of portal steps 1 to 9c becomes one command.

## Portal vs Bicep summary

| | Portal | Bicep |
|---|---|---|
| Time to build | Hours, step by step | One command, about 10 minutes |
| Repeatable | No, depends on following the guide | Yes, idempotent |
| Generated names | Some names chosen by the wizard | All names chosen |
| Data disk and Docker | Manual through Bastion | cloud-init on first boot |
| Drift detection | None | `what-if` shows any difference |
| Review | Screenshots | Pull request diff |
| Storage network access | Selected networks (`snet-app` + client IP) | All networks |

## Not covered by Bicep

| Item | Why |
|---|---|
| Porkbun nameservers | Outside Azure, done once (portal step 8e) |
| DNS zone and shared resource group | Created once, outlive the scenarios |
| Compose stack and application | Application deployment (portal steps 9d, 11, 12) |
| Backups | Not implemented by design (portal step 10) |
